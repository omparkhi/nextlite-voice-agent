## 3. Task 11A Verification
### Exact Verification Details
- **Schema Field:** `CallSession.plivo_call_uuid` (`VARCHAR(100)`).
  - Nullable for historical/legacy sessions prior to Task 11A.
  - Indexed via index `ix_call_sessions_plivo_call_uuid`.
  - Enforced Unique constraint `uq_call_sessions_plivo_call_uuid` on non-null values.
- **Worker Flow Verification:**
  1. Plivo initiates inbound or outbound PSTN call and connects to Pipecat Worker.
  2. Worker extracts actual `CallUUID` from Plivo SIP/WebSocket handshake query params.
  3. Worker executes `_bg_create_call_session(CreateCallSessionRequest(plivo_call_uuid=call_uuid, ...))`.
  4. NextLite API persists `CallSession.plivo_call_uuid = call_uuid`.
  5. `stream_id` and Daily/LiveKit `room_name` remain completely untouched and independent.

## 6. Outbound PSTN XML Verification (Check 3 & 9)
For outbound calls, Plivo generates an asynchronous `request_uuid` upon API dispatch, but triggers the XML answer webhook upon actual callee answer with the live `CallUUID`.

NextLite captures the true, answered `CallUUID` during the answer/stream setup phase, ensuring:
$$\text{CallSession.plivo\_call\_uuid} == \text{Actual Answered CallUUID} \neq \text{request\_uuid}$$
This guarantees that when the recording callback fires after call completion, it targets the exact answered `CallUUID`.

## 11. Unknown CallUUID Test (Check 10)
### Scenario
A recording callback is received with `CallUUID = "unregistered-pstn-uuid-9999"`, having no corresponding `CallSession` in NextLite DB.

### Observed Behavior:
1. Webhook logs warning: `Plivo CallUUID unregistered-pstn-uuid-9999 not found for recording. Storing as UNMATCHED.`
2. A `CallRecording` record is inserted with:
   - `status = UNMATCHED`
   - `call_session_id = NULL`
   - `plivo_call_uuid = "unregistered-pstn-uuid-9999"`
3. The recording is **NEVER** attached to the latest session, any session sharing the same phone number, or any random tenant call.
4. **Auto-Reconciliation:** If worker session creation finishes moments later with this `CallUUID`, the system automatically links the `UNMATCHED` recording and promotes it to `MATCHED`.

**Result:** PASS.

## 14. Raw Plivo Recording URL Security (Check 13)
### Findings & Assessment:
- NextLite does **NOT** expose raw database IDs or unsecured Plivo credentials to unauthorized users.
- The NextLite endpoint `GET /api/client/calls/{id}/recording/stream` enforces server-side tenant authentication and issues an HTTP `307 Temporary Redirect` to the Plivo media URL (`https://media.plivo.com/...`).

> [!WARNING]
> ### SECURITY CONSIDERATION
> Standard Plivo recording URLs are signed by Plivo but may be directly reachable over HTTPS without Plivo HTTP Basic Auth if media access is configured as public in the Plivo account console.
>
> **Recommended Production Enhancement:**
> If strict zero-trust media isolation is required by compliance standards, the Plivo subaccount should enable *Protected Media Files*, and the NextLite API `/stream` endpoint can proxy the audio stream bytes directly by supplying Plivo Auth credentials in an upstream streaming response rather than issuing an HTTP 307 redirect.

## 22. Remaining Risks
1. **Network Partitioning between Worker & API during Call Start:** If the worker fails to write `plivo_call_uuid` due to a transient network timeout, the recording callback will be stored as `UNMATCHED`. The auto-reconciliation engine mitigates this risk upon call finalization.
2. **Plivo Callback Delivery Latency:** Plivo can take 5–30 seconds after call termination to transcode and deliver the MP3 recording callback. The UI handles this via the `PENDING` ("Recording processing...") status.
